# Occulis

Jeu de plateau tactique compétitif 1v1 en ligne, vue isométrique 2D, DA en pixel art léger, mystique et cryptique (dessin procédural rendu en basse résolution, pas de sprites — design.md 8.1). Squelette conceptuel proche des échecs (roi à protéger, victoire par mat) mais sur une carte à géométrie libre avec hauteur, murs, ligne de vue (LOS) et fog of war.

**Le document de référence pour toute décision de game design est [docs/design.md](docs/design.md).** Il capture l'état exact des règles validées, l'historique des itérations (pourquoi certaines idées ont été écartées — ne pas les reproposer sans relire la section 6), et la liste des points encore ouverts (section 10). Avant de trancher une règle de gameplay non couverte par ce fichier, vérifier la section 10 : si le point y est listé comme ouvert, c'est une vraie décision à soumettre à l'utilisateur, pas à improviser silencieusement.

## Stack et architecture

- Monorepo pnpm workspaces, TypeScript strict partout.
- `packages/core` — logique de jeu pure (règles, plateau, hauteur, calcul de LOS, résolution des tours). **Aucune dépendance de rendu.** Testée avec Vitest.
- `packages/i18n` — **tous les textes affichés**, en anglais (langue par défaut et langue source) et en français, par domaine (`ui`, `game`, `auth`, `account`, `profile`, `admin`, `mail`…). Le dictionnaire français est typé sur la forme de l'anglais : une clé oubliée ne compile pas. Un message paramétré est une fonction, jamais une chaîne à trous. Pur et sans dépendance — le serveur s'en sert pour ses courriers. Voir la section « `locale/` » de `docs/technical/engine.md`.
- `packages/protocol` — les messages échangés entre le client et le serveur, et rien d'autre : aucune règle de jeu (elle vit dans `core`), aucun transport (il vit dans chaque app). Paquet partagé et non module de `apps/server`, précisément pour que les deux côtés ne puissent pas diverger.
- `apps/server` — Worker Cloudflare + Durable Objects, consomme `@occulis/core`. Transport, cycle de vie des DO, schéma D1, file d'attente de matchmaking et salons privés, jetons de siège. Comptes, sessions et matchmaking authentifié. **Elo** sur les seules parties de la file rapide (`rating.ts`, K = 32), sans aucun classement ; **faits d'armes** recalculés depuis les parties (`feats/`) ; **déploiement** des équipes dans le `MatchDO` (alarme à l'échéance, pièces de départ écrites dans `matches.setup`, dont repart tout rejeu) ; **équipes préparées** (`me/presets.ts`). L'authentification est portée par **Better Auth**, configuré dans `auth/better-auth.ts`, tournant dans le Worker sur la D1 du projet — aucun tiers ne détient l'identité. Le hachage PBKDF2 du projet y est branché, et `players` reste le profil de jeu, distinct du compte. **Le schéma de ses tables est généré (`pnpm --filter @occulis/server auth:schema`), jamais édité à la main.** Les modules purs (`seating.ts`, `pairing.ts`, `rooms.ts`, `admin/paging.ts`) portent les tests ; `match-do.ts` et `queue-do.ts` touchent le runtime. **Back-office** : le compte passe par le greffon `admin` de Better Auth (`/api/auth/admin/*`), les parties et le pseudo par `admin/` (`/api/admin/*`) ; la garde de rôle est **toujours côté serveur**. Le pseudo vit dans `users.name` _et_ `players.handle` : il ne se change que par `POST /api/me/handle` (le joueur, une fois par 30 jours) ou `POST /api/admin/players/:id/handle`, passe toujours `auth/handle.ts` (`checkHandle()`), et les routes `update-user` de Better Auth le refusent. **Profil** : `me/` (`/api/me/*`), chaque requête bornée à l'identifiant de la session ; **une session d'usurpation y est en lecture seule**, comme sur les routes de compte de Better Auth (`ACCOUNT_MUTATIONS`). **Google** est branché (liaison automatique, pseudo dérivé, proxy OAuth par la recette pour les branches) ; Google n'est volontairement **pas** un `trustedProvider`. **Amis** : `social/` (`/api/friends/*`, `/api/players/search`, `/api/blocks/*`, même garde que `me/` via `auth/guard.ts`, adresse vérifiée exigée) et `social-do.ts` (`SocialDO`, **un par joueur** : présence, poussées, défis) ; `social/relations.ts`, `chat.ts` et `search.ts` sont purs. Un **spectateur** passe par `/match/:id/watch`, gardé par le Worker, et ne reçoit que la vue du camp de son ami (design.md 5.5) — rien pendant le déploiement.
- `packages/ui` — la charte graphique en composants React (`@occulis/ui`) : tokens, une feuille de style unique (`occ-*`), environ soixante-dix briques. **`src/tokens.ts` est le seul fichier du projet autorisé à contenir une valeur de couleur** — une règle ESLint le vérifie en TypeScript, des tests dans la feuille ; `src/generated/tokens.css` en est généré, jamais édité. Synchronisée vers le projet Claude Design « Occulis UI » par `.design-sync/` (procédure et pièges dans `.design-sync/NOTES.md`). Voir `docs/technical/ui.md`.
- `apps/web` — rendu (Vite + PixiJS/WebGL), consomme `@occulis/core`, `@occulis/protocol` et `@occulis/ui`. La rotation isométrique et les recalculs de projection vivent ici (`src/view/iso.ts`), jamais dans `core`. `src/theme/theme.ts` reprend les couleurs de `@occulis/ui/tokens` et y ajoute métriques, alphas et épaisseurs du rendu PixiJS. **Le dossier dit la dépendance** : `view/` (projection, caméra, désignation, animation), `game/` (partie, sélection, scénario, hypothèse), `net/session.ts`, `ui/flow.ts`, `load/cache.ts`, `admin/model.ts`, `replay/replay.ts`, `admin/design/catalog.ts` et `admin/design/tweaks.ts` sont purs — ni Pixi ni DOM — et portent tous les tests ; `render/pixi/` dessine (Pixi, chargé à part par `render/pixi/board.ts` : le menu ne le télécharge pas), `input/` écoute le canevas, `ui/` touche le DOM par ailleurs et `net/channel.ts` ouvre le WebSocket. `admin/` est le back-office, seconde page Vite servie sous `/admin/`, et `profile/` la page de profil sous `/profile/`, toutes deux **en React sur `@occulis/ui`**, sans Pixi ni classe ou couleur propres — ce qui manque à une vue s'ajoute à la charte. L'écran de compte (`account/`) est un îlot React sur la charte dans la page du jeu, **un formulaire et une URL par parcours** (`/sign-in`, `/sign-up`, `/forgot-password`, `/reset-password`) pour les gestionnaires de mots de passe ; les autres écrans du jeu restent en DOM natif pour l'instant. `vite.config.ts` expose les maquettes de `docs/mockups/` sous `/mockups` en développement et sous `build:local`, jamais en production — voir la section correspondante de `docs/technical/engine.md`.
- Séparation logique/rendu actée dès le départ (docs/design.md section 8) pour permettre un futur portage moteur (C++ envisagé mais explicitement reporté, hors scope pour l'instant).
- Le serveur et son infrastructure sont **en place** — voir la section « Infrastructure et CI/CD » plus bas et [docs/architecture.md](docs/architecture.md). Le multijoueur en ligne fonctionne (file d'attente, sièges, parties arbitrées) ; le serveur est **autoritaire** et ne transmet jamais au client des données hors LOS de ce joueur. Ne pas casser ça : le fog est appliqué à la source, pas masqué à l'affichage — sinon il est contournable via devtools. Le client ne reconstruit qu'une **hypothèse** de la position depuis sa vue (`game/hypothesis.ts`), volontairement optimiste : elle peut proposer des coups que le serveur refuse, jamais en escamoter.

## Commandes

```bash
pnpm install
pnpm dev          # lance apps/web (Vite) — les maquettes sont servies sur /mockups
pnpm test         # tests de tous les paquets qui en déclarent (Vitest)
pnpm local        # serveur complet en local : build:local + migrations locales + wrangler dev (= pnpm infra → « Lancer le serveur en local »), /mockups et /lab compris
pnpm typecheck
pnpm lint         # zéro avertissement toléré
pnpm format       # Prettier ; la CI vérifie par pnpm format:check

```

## Conventions

- **Tout le nommage est en anglais** : identifiants, routes (`/sign-in`, `/profile/`), paramètres d'URL, fragments, clés de stockage. **Aucun texte affiché n'existe en français seul** : il passe par `@occulis/i18n`, en anglais et en français (côté client `messages()` ou `useMessages()`, côté HTML statique `data-i18n`). Les anciennes adresses françaises redirigent (`apps/server/src/legacy-routes.ts`) — des courriers déjà envoyés les portent. Les commentaires et la documentation restent en français.
- **Chargement et premier rendu : un écran paraît d'un seul tenant.** Aucune partie d'un écran ne s'affiche avant les autres — ni cadre vide, ni squelette, ni bloc qui arrive après le reste en le poussant. Toute page HTML reçoit au build le bloc `criticalHead()` (`@occulis/ui/critical` : fond et thème sombre en ligne, fondu entre pages, préchargement au survol) — jamais de couleur ni de `var(--occ-bg)` dans un `index.html`. Côté React : ce qu'un écran lit est déclaré par route (`resources.ts`, `resourcesOf(route)`) et préchargé ensemble ; une vue lit par `useLoad(resource)`, qui **suspend** ; une seule frontière `Suspense` par page, autour de tout l'écran ; les navigations passent par `useHashRoute` (transition : l'écran courant reste jusqu'à ce que le suivant soit complet). Jamais de `useEffect` + `fetch` à la main, jamais d'état « chargement » dans une vue, jamais d'entrée en cascade. Côté DOM natif (page du jeu) : tout ce qu'un écran montre part ensemble, et l'écran n'est montré qu'une fois tout arrivé ; un îlot React est rendu avant que son écran soit montré. Le détail est dans la section « Chargement et premier rendu » de `docs/technical/engine.md`.
- **La documentation technique de [docs/technical/](docs/technical/) se met à jour dans le même commit que le code qu'elle décrit.** Elle explique le fonctionnement réel de bout en bout, fonction par fonction, avec leur emplacement : `core.md` (`packages/core`), `engine.md` (`apps/web`), `server.md` (`apps/server`), `ui.md` (`packages/ui`), `infra.md` (`tooling/infra` et la CI) ; `packages/protocol` et `packages/i18n` sont décrits dans `server.md` et `engine.md`. Une fonction ajoutée, renommée, supprimée ou déplacée, un comportement modifié, un invariant touché → corriger le document du paquet concerné avant de considérer le changement comme terminé. Une doc de référence fausse est pire que pas de doc : elle fait perdre du temps en donnant l'illusion d'être fiable. Le _pourquoi_ d'une décision reste dans `docs/design.md` ou `docs/architecture.md`, jamais dans `docs/technical/`.
- Toute nouvelle règle de gameplay implémentée dans `packages/core` doit correspondre à une décision déjà actée dans `docs/design.md`. Si elle correspond à un point ouvert (section 10), demander avant d'implémenter plutôt que de choisir une interprétation arbitraire — plusieurs points (ex: attaque à distance combinable avec un déplacement, résolution des zones qui se chevauchent) ont un impact direct sur l'équilibrage.
- La LOS est calculée par raycast 2D (`packages/core/src/los.ts`, type Bresenham) avec comparaison de hauteur interpolée case par case — pas de moteur 3D. Voir docs/design.md section 5.1 pour le raisonnement.
- Grille : coordonnées entières `{x, y}` + hauteur de case séparée (`Tile.height`), jamais un simple array de valeurs numériques (cf. décision fondatrice section 5.1).
- Différenciation des pièces par capacité/mouvement, jamais par points de vie/robustesse.
- Pas de commentaires qui expliquent le "quoi" — seulement le "pourquoi" quand une règle de design non évidente est encodée (référencer la section du design doc au besoin).
- **`packages/core` doit rester strictement déterministe** : aucun `Math.random`, aucun `Date.now`, aucune source d'entropie ou d'horloge. Toute la persistance et tous les replays reposent sur le fait que rejouer un log d'actions reconstruit l'état exact (docs/architecture.md section 3). Un appel non déterministe introduit ici casserait silencieusement la reconstruction côté serveur. Si un aléa devient nécessaire pour une règle, il doit entrer par un seed explicite passé en paramètre, jamais être tiré dans `core`.
- Après toute modification substantielle de règle actée avec l'utilisateur, envisager de mettre à jour `docs/design.md` en parallèle du code pour que les deux restent synchronisés.

## Infrastructure et CI/CD

Décidée et documentée dans [docs/architecture.md](docs/architecture.md) ; chiffrage dans
[docs/costs.md](docs/costs.md) ; procédure d'installation dans [docs/setup.md](docs/setup.md).
Le Worker (`apps/server`), le matchmaking, l'authentification et la CI/CD sont en place ; reste la distribution Electron.
Les points encore ouverts sont listés en section 7 d'architecture.md : demander avant de trancher,
comme pour la section 10 du design doc.

- **Hébergement : Cloudflare Worker + Durable Objects.** **1 Durable Object = 1 partie.** Il détient le `GameState` et les deux `PlayerKnowledge`, et envoie à chaque joueur son propre `viewFor()`. Le fog est donc structurel et non applicatif : un client ne peut pas recevoir ce que le DO ne lui envoie pas. Le DO étant mono-threadé, la sérialisation des tours est acquise — ne pas ajouter de verrous.
- **Un second DO, global, sert de file de matchmaking et de table des salons privés** : son mono-threading élimine par construction le double appariement, et c'est la raison pour laquelle les deux vivent au même endroit — les séparer rouvrirait la course entre « être apparié » et « voir son salon rejoint ».
- **Le DO doit hiberner.** Un DO qui garde un WebSocket ouvert sans hiberner coûte ~20 000 fois plus cher, sans aucune différence fonctionnelle visible. À couvrir par un test dédié.
- **Base : D1** (SQLite managé, natif Workers). Un DO n'est pas une base — aucune requête transversale entre DO n'est possible. Tout ce qui se cherche, se classe ou s'agrège (comptes, ELO, historique, classement, amis) va en D1.
- **Le log d'actions en D1 est la source de vérité ; l'état du DO est un cache reconstructible.** Cela dépend entièrement de l'invariant de déterminisme de `core` ci-dessus.
- **Les règles sont versionnées par partie, pas par connexion.** Une partie démarrée sous le ruleset v3 se termine en v3. La cible étant une app téléchargeable (Electron), un vieux client embarque un vieux `core` ; et le pilier « temps de réflexion illimité » implique des parties qui traversent les déploiements.
- **Quatre environnements** : local (`wrangler dev`, SQLite local), preview par branche (`occulis-<branche>.0kl.fr`), recette (`occulis-staging.0kl.fr`), prod (`occulis.0kl.fr`, sur `main`). **Une branche = un environnement complet** (client + Worker + DO + base), jamais un preview du client seul : une branche qui touche `core` change les règles et serait sinon testée contre celles de `main`.
- **Les branches hébergées sont sélectionnées explicitement**, pas déployées automatiquement : on doit pouvoir en ajouter et en retirer à volonté, pour que la population d'environnements soit décidée et non subie. Le mécanisme est le manifeste `.github/deploy-environments.json`, édité dans les deux sens par `pnpm infra` (« Créer / Supprimer un environnement de branche »). La création part de la branche courante ; la suppression vise une cible explicite et marche depuis n'importe quelle branche, un environnement devant rester défaisable après la fusion de sa branche.
- **CI/CD** : `.github/workflows/ci.yml`. Les vérifications (`typecheck → lint → test → build`) tournent sur toute branche et toute PR ; le déploiement ne concerne que les branches listées dans **`.github/deploy-environments.json`** (`main` → production, `staging` → recette). Une branche absente du manifeste passe la CI sans être déployée : c'est là le mécanisme de sélection des environnements. Les migrations D1 précèdent toujours le déploiement. Un workflow séparé, sur tag, buildera et signera les binaires Electron.
- **L'URL du serveur n'est pas encore un sujet dans le code** : aucune variable de ce type n'existe, et le client est servi par le Worker lui-même (binding `ASSETS`), donc de même origine — une URL relative suffira sur le web. La contrainte connue ne vaudra que pour la distribution Electron, où le client n'est plus de même origine : l'URL y sera injectée au build et donc **gravée dans le binaire distribué**, ce qui impose de la figer avant le premier build public.

## Modules de `packages/core`

- `coord.ts` — coordonnées, clés de hachage, adjacence (`orthogonal` / `octile`), distances.
- `board.ts` — `Tile` (hauteur + franchissabilité) et `Board` immuable. Un **mur est une case haute**, jamais un flag ; une case absente est hors-carte. `Board.fromAscii` construit un plateau depuis une carte texte (pratique en test).
- `pieces/` — **un type de pièce = une classe**.
  - `piece.ts` — `Piece`, l'enregistrement de données d'une pièce en jeu (identité, camp, position). Volontairement inerte et sérialisable : c'est lui qui traverse le réseau et que le log d'actions rejoue.
  - `piece-type.ts` — `PieceType`, classe abstraite qui porte le comportement (déplacement, vision, frappe) et sert de point d'extension par héritage. Elle seule y vit ; toute classe concrète a son propre fichier.
  - `configurable-piece-type.ts` — `ConfigurablePieceType`, pour un type décrit par des données plutôt que par une classe.
  - `roster/` — **une classe par fichier** (`scout.ts`, `commander.ts`, `pawn.ts`), assemblées par `index.ts`. **Provisoires** : elles donnent un lieu unique aux définitions que le client, le serveur et les tests partagent. Aucun roster n'est acté (design.md point ouvert 12) et rien ne doit s'équilibrer dessus. Leurs portées sont volontairement généreuses (implementation-notes 14) : une vérification de règle ne doit jamais s'appuyer dessus.
  - `ruleset.ts` — `Ruleset`, table `kind` → `PieceType` d'une partie, fournie par l'appelant et versionnée par partie.
- `los.ts` — raycast et LOS, **géométrie seule** : ce qu'une pièce voit réellement est défini par son type (`PieceType.canSee` / `fieldOfView`), jamais recalculé ailleurs à partir d'une portée brute. **Une pièce occulte la vue** comme un mur d'un niveau posé sur sa case ; l'occupation lui est passée en paramètre, il ne consulte aucun état de partie. La LOS est **symétrique par construction** (l'ordre des extrémités est canonicalisé avant le tracé de Bresenham, et les extrémités n'occultent jamais) ; ne pas casser cette propriété — c'est aussi pourquoi les pièces alliées occultent au même titre que les adverses.
- `movement.ts` — cases atteignables et portée de mêlée, avec les règles de verticalité de la section 5.3.
- `state.ts` / `actions.ts` — état de partie immuable, génération des coups légaux, application d'une action. `GameState.history` porte le log des coups joués, et `replay` le rejoue. Les erreurs sont retournées via `Result`, jamais levées. Une action ne fait que **déplacer** : la capture, la règle « échecs strict » et les nulles anti-blocage sont **retirées du moteur** (design.md 3.1, 7.1, 7.2 — suspendues, point ouvert 13). Une pièce ne peut ni traverser une autre pièce ni entrer sur sa case, alliée ou adverse ; c'est `movement.ts` qui l'applique. **Seul l'abandon termine une partie** : ni mat, ni pat, ni nulle.
- `fog.ts` — état _connu_ de chaque joueur (mémoire fantôme) et `viewFor`, qui produit la vue transmissible sans aucune donnée hors LOS. C'est ce que le serveur envoie. `MatchMemory` (`startMemory` / `advanceMemory` / `replayMemory`) y assemble une position et les deux connaissances : la mémoire fantôme dépend de **toutes** les positions traversées, donc reconstruire une partie depuis son log doit faire avancer la connaissance à chaque coup — le serveur et le client s'en servent tous les deux.
- `team.ts` — le déploiement : validation d'une équipe (quotas du ruleset, zone de la carte), pièces de départ aux identifiants déterministes, transposition d'une équipe du camp A au camp B.
- `rulesets/` — le registre des rulesets par version (`rulesetFor()`), partagé par le client et le serveur.
- `scenarios/` — positions de départ, une par fichier, assemblées par `index.ts`. **Provisoires** comme le roster. Une partie **fige sa carte à sa création** (`ScenarioSnapshot`, `matches.map`) et l'envoie au client dans `welcome` : retoucher une carte du registre ne change ni les parties en cours ni les replays. Aucune carte n'est actée (design.md point ouvert 5).
- `testing.ts` — fabriques de scénarios pour les tests uniquement.

## État du projet

Logique de jeu posée et testée (105 tests dans `core`) : plateau à hauteur, LOS occultée par le relief **et par les pièces**, verticalité, déplacement avec blocage mutuel des pièces, tours alternés, fog of war avec mémoire, historique et rejeu, abandon.

**Capture, échec et mat, pat et nulles ont été retirés** sur décision explicite du porteur du projet : la règle « échecs strict » n'était pas jouable avec les portées démesurées du roster provisoire (elle mettait la maîtresse en échec permanent et supprimait tous ses coups). On reconstruit d'abord la géométrie — déplacement, blocage, vision — puis on y reposera une prise et une fin de partie (design.md point ouvert 13). Conséquence : aujourd'hui, **une partie ne se termine que par abandon**.

Multijoueur en ligne fonctionnel de bout en bout (188 tests dans `apps/server`, 13 dans `packages/protocol`, 10 dans `packages/i18n`) : file d'attente, appariement, **salons privés désignés par un code**, jetons de siège, autorité de tour, diffusion des vues par joueur, log d'actions en D1 et clôture de partie. Vérifié en conditions réelles avec deux clients sur `wrangler dev`. Comptes et sessions portés par Better Auth (hachage PBKDF2 du projet conservé, cookie `HttpOnly` signé par `AUTH_SECRET`) ; la file d'attente n'accepte qu'un joueur authentifié **et vérifié**, et l'identité vient du cookie, jamais de la requête. Limitation de débit, vérification d'adresse, réinitialisation de mot de passe, refus des mots de passe ayant fuité (HIBP, échoue ouvert), courriers HTML et purge nocturne sont en place. **Connexion Google** (secrets `GOOGLE_*`, procédure en docs/setup.md section 7) et **page de profil** (`/profile/` : pseudo, adresse, mot de passe, Google, sessions, suppression par lien, historique et replay **de son seul point de vue**). Un **back-office** (`/admin/`, rôle `admin`) liste et modifie les comptes par des actions rapides (rôle, suspension, adresse, mot de passe, sessions, suppression, pseudo, **usurpation** d'une heure au plus, signalée par un bandeau dans le jeu), et montre les statistiques, l'historique de chaque joueur et les parties **rejouées coup par coup sur le plateau** (position complète et ligne de vue de chaque camp, calculées par le serveur), et un **design system** (`#/design`, `admin/design/`) : la charte montrée par ses propres sources — celles dont Claude Design est synchronisé, `.design-sync/` et `packages/ui/src/` —, composants montés en vrai avec leur code et leurs props, animations rejouables et ralenties, conventions, et des retouches à chaud (thème, palette copiable vers `tokens.ts`, vitesse) qui ne s'écrivent nulle part ; le premier administrateur se nomme à la main (docs/setup.md section 7). Un **système d'amis** complète le tout : demandes, recherche par préfixe et ajout depuis l'historique, blocage (jamais signalé au bloqué), présence en ligne, **messages privés** persistants (purgés à 90 jours), fiche d'un ami avec bilan, historique et replay **de son point de vue**, **défi direct** depuis le menu du jeu (non classé, droit au déploiement), et **spectateur** d'une partie d'un ami, de son côté seulement et s'il l'autorise. Gestion et messages dans le profil (`/profile/#/friends`), défier et regarder depuis le menu du jeu ; textes dans le domaine `social` de `@occulis/i18n`. Les valeurs choisies par défaut sont en implementation-notes 28 à 30. **Deux choses restent avant une mise en ligne publique** : provisionner `AUTH_SECRET` et `RESEND_API_KEY` par environnement (docs/setup.md section 7), et faire vérifier le domaine d'envoi chez Resend — sans quoi aucun message ne part.

Trois pièges de ce socle, tous vérifiés par des tests : Better Auth range ses échéances en **texte ISO 8601**, donc les comparer à un nombre de millisecondes est toujours faux sans rien signaler ; sa limitation de débit **valide** l'en-tête `CF-Connecting-IP`, retombant sur un seau unique partagé si la valeur n'est pas une vraie adresse ; et **la bordure Cloudflare plafonne PBKDF2 à 100 000 itérations par appel quand le workerd local n'en plafonne aucune** — le hachage à 210 000 itérations passait donc tous les tests et rendait 500 sur chaque inscription en recette. Le coût OWASP est atteint en enchaînant six passes de 100 000. Cas particulier d'une règle plus large : **une suite verte dans workerd ne dit rien des limites de ressources de la bordure**, et le hachage impose à lui seul le plan Workers Paid (les 10 ms de CPU du plan gratuit n'y suffisent pas).

Moteur de rendu isométrique fonctionnel (243 tests dans `apps/web`, 69 dans `packages/ui`) en pixel art léger : plateau rendu dans un tampon réduit puis agrandi au plus proche voisin (`view/pixel.ts`, un pixel du plateau = deux pixels physiques), faces pleines aux arêtes d'os, fog tramé, voûte d'étoiles, police pixel Tiny5 dans toute l'interface. **Trois thèmes** à comparer (`THEMES` dans `tokens.ts`, `look()` dans `theme.ts`, fenêtre de réglages ouverte par l’engrenage, menu et partie) : Obsidienne, Reliquaire, Astral — non tranchés. **Toute action s'anime** (vague de ligne de vue, entrée du plateau, saut et retombée, cascade de sélection, matérialisation), en fonctions pures du temps dans `view/reveal.ts`, `view/effects.ts`, `view/easing.ts`, et **toute fenêtre ouverte par un clic se déplie** — un cadre d'un pixel qui s'étire jusqu'à ses bords, depuis la souris si elle est posée à côté du clic (réglages), depuis son centre sinon (modales, messages) (`revealWindow`, `@occulis/ui/reveal`) ; les écrans du parcours (menu, compte, attente, bandeau) paraissent sans, sauf l'entrée dans la recherche ou la création d'une partie, qui passe sous **le voile tramé du changement de thème** (`ui/veil.ts`) — **geste acté par le porteur du projet, verrouillé par `veil.test.ts` : ne jamais le retoucher sans sa demande explicite** ; zoom vers le curseur, déplacement, rotation libre aimantée sur le quart de tour, surbrillance de la case survolée, occlusion des pièces par le relief, fog of war à l'écran. La DA et la caméra sont actées provisoirement en section 8.1 du design doc.

**Il n'existe aucune partie locale** : le hot-seat a été retiré (implementation-notes 18). À l'arrivée sur la page, le canevas est masqué et c'est l'écran de compte (îlot React, `account/`) qui s'affiche ; le menu propose ensuite trois entrées — partie rapide, créer une partie (le serveur rend un code à transmettre), rejoindre avec un code. La machine à états des écrans est pure et testée (`ui/flow.ts`) ; `ui/shell.ts` la montre, `net/queue-channel.ts` porte l'unique canal de file par lequel passent les trois intentions.

**Préparation d'une partie** : la file rapide propose la partie aux deux joueurs, qui doivent l'accepter en 15 s (`proposals.ts`, îlot `prepare/MatchFound.tsx`) ; les salons privés passent directement au déploiement. Le déploiement (90 s) annonce l'adversaire — pseudo, Elo, bilan, faits d'armes exhibés — puis chaque joueur compose son équipe (1 maîtresse, 3 pièces à capacité, 4 pions) et la pose dans sa zone (`prepare/Deployment.tsx` sur `team-builder/TeamBuilder.tsx`) ; à l'échéance, son brouillon complet ou l'équipe par défaut de la carte. Les équipes se préparent d'avance depuis le menu (`presets/`, `/api/me/presets`), la marquée par défaut se préchargeant. Les autres écrans du jeu (menu, attente, bandeau) restent en DOM natif ; les nouveaux sont des îlots React sur la charte.

Une fois en partie, un coup se joue de deux façons : **au clic** (sélectionner une pièce affiche ses destinations légales, cliquer une destination l'y déplace avec une animation) et **par saisie de coordonnées** (`1,6 2,5` déplace, `abandon` abandonne). Une pièce adverse n'est ni une cible ni une destination — seulement un obstacle. La sélection **filtre `legalActions`, elle ne redéduit jamais la légalité** (`game/selection.ts`). Il n'y a qu'un point de vue, celui du siège : le serveur n'envoie jamais la vue d'en face.

Non implémenté volontairement, car listé comme ouvert en section 10 du design doc : attaque à distance différée, pièges, roster de pièces définitif (seule la composition d'équipe est actée). Une charte graphique existe (`packages/ui`, synchronisée vers Claude Design) et porte le back-office, le profil, l'écran de compte et les écrans de préparation ; le menu, l'attente et le bandeau de partie n'y ont pas encore migré.

**Les interprétations qu'il a fallu encoder faute de décision explicite sont consignées dans [docs/implementation-notes.md](docs/implementation-notes.md)** — les relire avant de bâtir dessus, et faire valider celles qui sont concernées avant d'ajouter une règle qui en dépend.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships. It is built locally on each machine and never committed (`graphify-out/` is gitignored); setup and usage are in [docs/graphify.md](docs/graphify.md). If graphify-out/graph.json is missing, build it with `graphify update .`.

Rules:

- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
